# Как работает AI-агент в `agents0826/module1`

Разбор на реальном коде проекта. Здесь буквально весь механизм агента уместился в один файл на ~40 строк.

## 0. Главная идея — на пальцах

Представь, что ты — оператор поддержки почты. Тебе пишет клиент:
*«Посылка не пришла, хочу вернуть деньги за доставку»*.

У тебя на столе телефон с внутренней линией на склад, по которому можно
спросить статус посылки — и всё. Ты не можешь сам оформить возврат, у
тебя просто нет такой кнопки.

Что ты делаешь?

1. Смотришь на запрос клиента, думаешь: «нужно узнать статус».
2. Звонишь на склад, называешь трек-номер.
3. Слушаешь ответ склада.
4. Думаешь: «ага, а прав на возврат у меня всё равно нет» → честно
   пишешь клиенту, что не можешь оформить возврат.

Вот это **и есть весь AI-агент**: LLM (языковая модель) вместо тебя
думает, «звонит» (вызывает функции-инструменты), получает результат и
решает, что дальше — повторить звонок, позвонить ещё раз в другое
место, или уже ответить клиенту.

Цикл называется **think → act → observe** («думай → действуй →
наблюдай»), и именно так он назван в коде: `core/agent.py:5` —
*«Цикл «міркуй → дій → спостерігай»»*.

## 1. Карта проекта

```
run.py / demo.py     — точки запуска (просто скрипты, которые дёргают агента)
config.py            — настройки: ключ API, какая модель, лимиты
modules/m01_core.py  — "модуль 1": собирает агента из кусочков
core/agent.py        — САМ ЦИКЛ агента (сердце всего)
core/escalation.py   — что делать, если агент не справился → передать человеку
core/cost.py         — сколько стоил прогон в долларах
domain/backend.py    — "фейковый склад": инструменты + база посылок
```

## 2. Сердце — `core/agent.py`

Вот упрощённо, что происходит в функции `run_agent` (`core/agent.py:73`):

```python
messages = [{"role": "user", "content": query}]   # кладём вопрос клиента

for turn in range(MAX_TURNS):        # не более 6 попыток подряд
    resp = вызвать_модель(messages, tools=список_инструментов)

    если модель хочет ответить текстом:
        вернуть готовый ответ            # ← готово, цикл закончен

    иначе модель хочет вызвать инструмент:
        выполнить инструмент             # ← "позвонить на склад"
        добавить результат в messages    # модель это увидит на следующем шаге
        # цикл идёт по новому кругу
```

Важно понять: **модель сама решает**, вызывать инструмент или нет. Ей
просто дают список доступных «кнопок» (`tools`), а она пишет: «хочу
нажать вот эту, с такими параметрами». Код (`domain/backend.py`)
реально нажимает кнопку и отдаёт результат обратно модели её же
словами.

## 3. Что такое «инструмент» (tool)

Это просто обычная Python-функция плюс её «паспорт» — описание для
модели, что она делает и какие у неё параметры. Пример из
`domain/backend.py:56`:

```python
def get_order_status(tracking: str) -> dict:
    o = ORDERS.get(tracking.strip().upper())
    ...
    return {"tracking": ..., "status": ..., "days_in_transit": ...}
```

И рядом — описание для модели (`domain/backend.py:150`):

```python
"get_order_status": _schema(
    "get_order_status",
    "Повертає статус відправлення за трек-номером.",
    {"tracking": {...}}, ["tracking"])
```

Модель читает это описание и понимает: «если хочу узнать статус — надо
вызвать `get_order_status` и передать `tracking`».

`ORDERS` в этом файле — это фейковая база данных из 5 посылок
(просроченная, потерянная, доставленная вовремя, ушедшая обратно
из-за неверного адреса и т. д.) — чтобы было на чём тестировать разные
ситуации.

## 4. Права агента ограничены нарочно — `CAPABILITIES`

Это ключевая фишка именно **модуля 1**. Инструментов в
`domain/backend.py` описано пять: посмотреть статус, проверить право
на возврат доставки, проверить компенсацию, создать претензию,
передать человеку. Но в модуле 1 агенту выдают только один:

```python
CAPABILITIES = {1: BASIC, ...}   # BASIC = ["get_order_status"]
```

Смотри `domain/backend.py:180`. То есть агент физически **не может**
вызвать `check_refund_eligibility` или `create_claim` — этой кнопки у
него на пульте просто нет. Отсюда логика README: агент может только
посмотреть статус и должен честно сказать «оформить возврат нечем» —
не потому что он «не умный», а потому что ему не выдали инструмент.

Это специально сделано педагогически: в следующих модулях курса будут
добавлять новые инструменты, и агент «поумнеет» не потому, что модель
стала другой, а потому, что ему дали больше прав.

## 5. Проследим реальный прогон шаг за шагом

Запрос из `config.py:39`:

> «Посилка EE123456789UA не прийшла вже два тижні. Я хочу повернути
> гроші за доставку.»

Что происходит внутри `run_agent`:

**Шаг 1 (turn=0).** Модель получает вопрос + системный промпт («ты
ассистент поддержки») + список инструментов = `[get_order_status]`.
Модель думает: «чтобы ответить — надо узнать статус посылки», и вместо
текстового ответа возвращает `stop_reason == "tool_use"` с вызовом
`get_order_status(tracking="EE123456789UA")`.

**Действие.** Код в `agent.py:114` реально выполняет
`dispatch("get_order_status", {...})`, который лезет в `ORDERS` и
находит:

```
status: "В дорозі", days_in_transit: 15, declared_delivery_days: 5
```

Этот результат добавляется в переписку как будто это ответ
«инструмента» — модель это увидит.

**Шаг 2 (turn=1).** Модель снова вызывается, но теперь в истории уже
есть результат склада. Модели больше не нужно ничего вызывать (второго
нужного инструмента у неё всё равно нет), поэтому она пишет финальный
текстовый ответ: что-то вроде «Посылка задержана на 15 дней при
заявленных 5, но оформить возврат средств за доставку я не могу —
обращайтесь к оператору / у меня нет инструмента для этого».

`stop_reason != "tool_use"` → цикл заканчивается, `outcome = "ok"`.

## 6. Пять исходов (outcome) — это дисциплина, а не украшение

В `core/agent.py` явно обработаны все ветки, а не только «счастливый
путь»:

| outcome | когда происходит | что видит клиент |
|---|---|---|
| `ok` | модель дала финальный ответ | обычный ответ |
| `no_tool_used` | модель ответила текстом, ни разу не вызвав инструмент | подозрительно — модель могла придумать факты «из головы» |
| `tool_error` | инструмент вернул `{"error": ...}` | если агент так и не смог обойти ошибку |
| `turns_exhausted` | за `MAX_TURNS` (6) шагов агент не закончил | «Не вдалося завершити за відведену кількість кроків» |
| `api_error` | сам вызов Anthropic API упал (после 3 ретраев) | «Сервіс тимчасово недоступний» |

Демо-сцена 2 в `demo.py:38` специально проверяет «ловушку»: вопрос про
погоду. Инструмента «узнать погоду» нет вообще, значит если модель всё
равно «ответит из головы» — это баг (`no_tool_used=True` при
`trace=[]`), и такой агент опаснее, чем агент, который молчит и
передаёт человеку.

Демо-сцена 3 (`demo.py:44`) искусственно ставит `MAX_TURNS=1`, чтобы
показать `turns_exhausted` — агент физически не успевает и туда, и
обратно за один шаг.

## 7. Эскалация — `core/escalation.py`

Если агент не справился (любой «плохой» outcome, клиент сам попросил
оператора и т. п.) — `escalation.decide()` выбирает причину, и
`escalation.apply()` создаёт тикет через `escalate_to_human()` вместо
того, чтобы агент придумывал что-то от себя. Это тот самый принцип из
README: **«агент, который не врёт и не падает»** — если не уверен,
передаёт человеку, а не выдумывает.

## 8. Экономия — `config.py` и `core/cost.py`

Заметь в `config.py:20`:

```python
MODEL      = "claude-sonnet-4-6"        # думает — сам цикл агента
MODEL_FAST = "claude-haiku-4-5..."      # вспомогательные вызовы (роутер, проверки)
```

Дорогая модель используется только там, где реально нужно рассуждение
(сам цикл агента), а дешёвая — для простых вспомогательных задач.
`core/cost.py` потом считает, сколько реально стоил прогон и сколько
сэкономили на этом каскаде моделей.

## 9. Как всё это запустить

```bash
python run.py          # прогоняет запрос через модуль(и), сохраняет в out/responses.json
python demo.py         # 3 показательные сценки (успех / ловушка / лимит шагов)
```

## Итог

Агент = LLM в цикле, у которой есть ограниченный набор «кнопок»
(функций); она сама решает, когда какую нажать, а код вокруг честно
ловит все виды провалов и передаёт человеку, когда не справляется
сама. Модуль 1 специально даёт агенту только одну кнопку
(`get_order_status`), чтобы показать: агент честно скажет «не могу», а
не начнёт выдумывать.
