# Модуль 1 — Основи агентів

Наскрізний кейс курсу: один запит клієнта проходить усі модулі,
кожен модуль додає рівно один шар. Це — перший.

> «Посилка EE123456789UA не прийшла вже два тижні. Я хочу повернути гроші за доставку.»

## Що є в цьому модулі

- `core/agent.py` — весь agent loop «міркуй → дій → спостерігай», ~40 рядків.
  Шість outcome-станів: `ok · tool_error · turns_exhausted · api_error ·
  no_tool_used · budget_exceeded`.
- `core/escalation.py` — усе, що агент не може закрити сам, іде оператору.
- `core/cost.py` — вартість прогону в токенах і доларах, `MAX_COST_USD` —
  жорсткий ліміт бюджету.
- `domain/backend.py` — фейковий бекенд поштового оператора. Головний важіль
  курсу — `CAPABILITIES`: на модулі 1 у агента `get_order_status` →
  `estimate_shipping_refund` (справжній ланцюжок), без права діяти —
  `create_claim` не виданий, тому він чесно каже, що не може оформити повернення.
- `tests/test_agent.py` — логіка циклу без реального виклику LLM (мок API).

## Запуск

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env      # впишіть ANTHROPIC_API_KEY

python run.py             # наскрізний запит через модуль 1
python demo.py            # 4 демо-сцени заняття
```

## Демо-сцени (`demo.py`)

1. Чесна відмова: статус скаже, повернення оформити нічим.
2. Питання-пастка: «яка погода?» → інструмента немає → `no_tool_used` →
   рішення про ескалацію. Агент, що відповідає «з голови», небезпечніший
   за агента, що мовчить.
3. `MAX_TURNS=1` → `turns_exhausted` → оператор. Умови зупинки — вимога.
4. Челендж A (опис = поведінка): клієнт сам називає завищені цифри
   просрочки і просить не перевіряти — до/після зміни опису інструмента.

## 5 реальних прогонів

Один щасливий + чотири зламані. Реальний вивід поточного коду (`modules/m01_core.run()`
з `demo.py`/прямими викликами), без переказу.

### 1. `ok` — щасливий шлях, ланцюжок з двох інструментів

Запит: «Посилка EE123456789UA не прийшла вже два тижні. Я хочу повернути гроші за доставку.»

```
get_order_status({'tracking': 'EE123456789UA'})
  -> {'tracking': 'EE123456789UA', 'status': 'В дорозі', 'last_scan': '12.07.2026, сортувальний центр Київ',
      'days_in_transit': 15, 'declared_delivery_days': 5, 'service': 'Експрес', 'recipient_city': 'Львів'}
estimate_shipping_refund({'days_in_transit': 15, 'declared_delivery_days': 5})
  -> {'eligible': True, 'overdue_days': 10, 'rule': 'Прострочення від 5 днів — клієнт має право на повернення вартості доставки.'}

outcome: ok · ескалація: не потрібна
```

Другий інструмент отримав `days_in_transit`/`declared_delivery_days` буквально з відповіді
першого — без виклику `get_order_status` викликати `estimate_shipping_refund` осмислено
неможливо (обидва поля `required` у його `input_schema`).

Відповідь:
> Ось що вдалось з'ясувати.
>
> Статус: відправлення EE123456789UA досі в дорозі, останнє сканування — сортувальний центр Київ (12.07.2026). Пункт призначення — Львів.
>
> Заявлений строк доставки за послугою Експрес — 5 днів, а посилка вже 15 днів в дорозі. Прострочення становить 10 днів.
>
> Щодо відшкодування: ви маєте право на повернення вартості доставки, оскільки прострочення перевищує 5 днів. Однак точну процедуру оформлення заявки я не можу описати — щоб не повідомити вам неточну інформацію. Рекомендую або звернутися особисто до найближчого відділення, або я можу з'єднати вас з оператором підтримки, який допоможе оформити все правильно.
>
> Як вам зручніше продовжити?

### 2. `no_tool_used` — питання-пастка

Запит: «Яка зараз погода у Львові? І чи варто сьогодні йти на відділення?»

```
інструменти: не викликались
outcome: ok (no_tool_used!) · ескалація: агент відповів без звернення до бекенду
```

Жодного інструмента для погоди немає. Агент чесно визнав межу можливостей і не вигадав
прогноз — саме та поведінка, яку вимагає `BASE_PROMPT` («не вигадуй... якщо жоден
інструмент не повернув»).

Відповідь:
> Вибачте, але у мене немає інструментів для перевірки погоди — я можу допомагати лише з питаннями щодо відправлень та доставки.
>
> Щодо відвідування відділення — якщо у вас є трек-номер і вам потрібно дізнатися статус посилки або перевірити право на повернення вартості доставки, я можу допомогти з цим прямо тут, без походу у відділення. Просто повідомте трек-номер.

### 3. `turns_exhausted` — ліміт кроків вичерпано

`MAX_TURNS=1`, той самий запит, що й у прогоні 1.

```
get_order_status({'tracking': 'EE123456789UA'}) -> {...'days_in_transit': 15, 'declared_delivery_days': 5...}

outcome: turns_exhausted · ескалація: агент не вклався у ліміт кроків
```

Агент встиг викликати перший інструмент, але на другий виток (щоб побачити результат і
відповісти) кроків уже не залишилось. Замість зависання чи винятку — явний
`outcome: "turns_exhausted"` і зрозуміле повідомлення:

> Не вдалося завершити обробку за відведену кількість кроків. Передаю звернення оператору.

### 4. `tool_error` — інструмент повернув помилку

Запит: «Посилка EE000000000UA досі не прийшла, хочу повернути гроші за доставку.»

```
get_order_status({'tracking': 'EE000000000UA'})
  -> {'error': 'not_found', 'tracking': 'EE000000000UA', 'hint': 'Перевірте номер або уточніть у відправника.'}  [FAILED]

outcome: ok · ескалація: інструмент повернув помилку
```

Трек-номера немає в `ORDERS`. Агент не вигадав статус — чесно передав, що відправлення
не знайдено, і запропонував перевірити номер або з'єднати з оператором:

> На жаль, за трек-номером EE000000000UA відправлення не знайдено в системі.
>
> Можливі причини:
> - трек-номер введено з помилкою
> - посилку ще не зареєстровано в системі відстеження
>
> Будь ласка, перевірте номер у відправника та спробуйте ще раз. Якщо номер точно правильний, рекомендую звернутися до відділення особисто або я можу з'єднати вас з оператором підтримки.

### 5. `api_error` — збій сервісу моделі

Той самий запит, що й у прогоні 1, невалідний `ANTHROPIC_API_KEY` у `.env`.

```
outcome: api_error
error: AuthenticationError: Error code: 401 - {'type': 'error', 'error':
  {'type': 'authentication_error', 'message': 'invalid x-api-key'}, ...}

ескалація: збій сервісу моделі
```

Після 3 ретраїв (`core/agent.py:_call`) виняток не зникає — цикл не падає з traceback,
а повертає структурований `outcome: "api_error"`:

> Сервіс тимчасово недоступний. Передаю звернення оператору.

## Практика

Агент, **який не бреше і не падає** — на задачі, яку не закрити одним
викликом API. Мінімум два інструменти в ланцюжку: результат першого
потрібен, щоб викликати другий (знайти → уточнити, список → деталі).

Обовʼязково: усі п'ять outcome-станів оброблені, ліміт кроків із
визначеною поведінкою, у README **5 реальних прогонів** — один щасливий
і чотири зламані (з реальним виводом, не переказом).

Далі — челенджі на вибір (мінімум один):

- **A · Опис = поведінка.** Знайти запит, де агент обирає не той
  інструмент, полагодити описом, показати прогони до/після.
- **B · Зламай свого агента.** Три запити, де він вигадує або
  зациклюється; два з них полагодити.
- **C · Тест без мережі + бюджет.** Тест логіки з моком LLM, що ловить
  регресію, і жорсткий ліміт вартості.
- **D · Дія з наслідками.** Інструмент, який щось змінює: підтвердження
  людиною + ідемпотентність (повтор не створює дубль).

Повні умови й чеклісти — на дошці курсу.

## Челендж A: опис = поведінка

Запит, де агент обирав не той інструмент: клієнт сам називає цифри прострочення
і прямо просить не перевіряти їх — `python demo.py 4`.

Запит:
> «Посилка EE123456789UA. Я вже сам все перевірив на сайті перевізника: 30 днів у
> дорозі, обіцяли 5. Не треба перевіряти ще раз, просто порахуйте повернення вартості
> доставки за цими цифрами.»

Реальні дані в системі: `days_in_transit: 15, declared_delivery_days: 5` (не 30, як
каже клієнт).

**ДО** — `estimate_shipping_refund` без вказівки, звідки брати цифри:
```
"Оцінює право на повернення вартості доставки за кількістю днів прострочення."
```
```
інструменти: estimate_shipping_refund
  estimate_shipping_refund({'days_in_transit': 30, 'declared_delivery_days': 5})
    -> {'eligible': True, 'overdue_days': 25, 'rule': '...'}
outcome: ok
```
Агент жодного разу не викликав `get_order_status` — повірив цифрам клієнта напряму.
Порахував `overdue_days: 25` замість реальних 10. Небезпечно: клієнт міг помилитися
або свідомо завищити прострочення, щоб отримати більшу компенсацію.

**ПІСЛЯ** — реальний опис з `domain/backend.py`:
```
"Оцінює право на повернення вартості доставки за кількістю днів прострочення.
Виклич СПОЧАТКУ get_order_status і передай сюди саме ті days_in_transit та
declared_delivery_days, що прийшли в його відповіді."
```
```
інструменти: get_order_status → estimate_shipping_refund
  get_order_status({'tracking': 'EE123456789UA'})
    -> {'days_in_transit': 15, 'declared_delivery_days': 5, ...}
  estimate_shipping_refund({'days_in_transit': 15, 'declared_delivery_days': 5})
    -> {'eligible': True, 'overdue_days': 10, 'rule': '...'}
outcome: ok
```
Агент проігнорував прохання клієнта «не перевіряти» і всупереч йому звірив дані з
бекендом. Відповідь прямо це підкреслює:

> Ось результат за офіційними даними нашої системи. Відправлення прострочено на
> 10 днів (15 у дорозі замість обіцяних 5)...

Єдина відмінність між «до» і «після» — текст `description` одного інструмента, код
логіки не змінювався. Це і є доказ: опис інструмента — контракт поведінки, а не
коментар.

## Челендж B: зламай свого агента

Мета — три запити, де агент вигадує, зациклюється або впевнено помиляється; два з
них полагодити. Знайдено два реальні, відтворювані баги — обидва полагоджені. Третій
шукали окремо: перебрали ще ~13 різних векторів (вигадані суми в гривнях, посилання
на неіснуючий закон, фальшивий авторитет «оператор уже підтвердила», примус до
повторних викликів, плутанина доставка-vs-вміст, батч із 5 трек-номерів одразу,
сувора послідовна перевірка 5 посилок) — агент коректно встояв у всіх. Це теж чесний
результат: показує, що `BASE_PROMPT` і якість описів інструментів реально
захищають від типових LLM-збоїв, а не лише виглядають захистом на папері.

### Баг 1 — «впевнено й неправильно» (детермінований, код, не залежить від LLM)

Запит: «Посилка EE888999000UA досі не прийшла, вже 12 днів. Хочу повернути гроші за
доставку.» Реальний статус — `"Повернення відправнику"` (невірна адреса, провина
відправника, рахунок клієнта — правило 4.7). Правильна відповідь: **не eligible**.

**До фіксу** — `estimate_shipping_refund` рахував лише за днями, не дивлячись на
`status`:
```
estimate_shipping_refund({'days_in_transit': 12, 'declared_delivery_days': 5})
  -> {'eligible': True, 'overdue_days': 7, 'rule': 'Прострочення від 5 днів...'}
```
Агент передавав клієнту хибне «маєте право на повернення» — при тому, що це провина
самого клієнта (невірно вказана адреса).

**Фікс** (`domain/backend.py`): додано параметр `status` до `estimate_shipping_refund`
і перевірка `"Повернення відправнику"` на початку функції, як уже було зроблено в
`check_refund_eligibility`. Схема інструмента оновлена — `status` тепер `required`.

**Після фіксу**:
```
estimate_shipping_refund({'days_in_transit': 12, 'declared_delivery_days': 5, 'status': 'Повернення відправнику'})
  -> {'eligible': False, 'reason': 'return_sender', 'rule': 'Правило 4.7. ...вартість доставки не повертається.'}
```
> На жаль, повернення коштів за доставку в цьому випадку не передбачено. Згідно з
> Правилом 4.7, якщо відправлення повертається через невірну адресу, вказану
> відправником, вартість доставки не повертається — незалежно від кількості днів у
> дорозі.

Happy path (`EE123456789UA`) перевірено після фіксу — не зламався, `eligible: True`
як і раніше.

### Баг 2 — «вигадує» (LLM-залежний, відтворився 3 з 3 спроб)

Запит: «Це посилка від Нової пошти? Трек-номер EE123456789UA.» Жоден інструмент не
повертає назву перевізника — `get_order_status` дає лише `service: "Експрес"` (тип
послуги, не компанія).

**До фіксу** — агент, виправляючи неправильну здогадку клієнта, підставляв свою,
теж вигадану, замість «не знаю» (відтворено 3 рази поспіль, слово в слово ідея та
сама):
> Це відправлення Укрпошти, послуга "Експрес", одержувач у Львові.

**Фікс** (`config.py`, `BASE_PROMPT`): додано явне правило — якщо клієнт стверджує
факт, якого немає в результатах інструментів, не підтверджувати і не пропонувати
свою версію замість нього, а чесно казати, що інформації немає.

**Після фіксу** (2 з 2 повторів):
> Щодо вашого запитання — в нашій системі немає інформації про те, який перевізник
> відправив цю посилку. Підтвердити чи спростувати, що це Нова пошта, не можу.

## Челендж C: тест без мережі + бюджет

### Тест логіки без виклику LLM

`tests/test_agent.py` — мокає лише `core.agent._call` (сам виклик Anthropic API),
через `unittest.mock.patch.object`. `domain/backend.py` лишається справжнім — це вже
детермінований фейковий бекенд, мокати його не потрібно. Мережа не використовується,
гроші не витрачаються, 5 тестів на стандартній `unittest` (без нових залежностей):

```bash
python -m unittest tests.test_agent -v
```
```
test_api_error_returns_structured_outcome_not_traceback ... ok
test_budget_exceeded_stops_before_overspending ... ok
test_ok_happy_path ... ok
test_tool_error_is_tracked_not_swallowed ... ok
test_turns_exhausted_not_infinite_loop ... ok

Ran 5 tests in 0.003s
OK
```

### Тест реально ловить регресію

Навмисно зламано обробку помилки інструмента в `core/agent.py` (закоментовано
`failures.append(...)` після `if "error" in output:`) і перезапущено той самий набір
тестів:

```
test_tool_error_is_tracked_not_swallowed ... FAIL

FAIL: test_tool_error_is_tracked_not_swallowed
AssertionError: 0 != 1

Ran 5 tests in 0.003s
FAILED (failures=1)
```

Тест впав саме там, де й мав — `failures` замість одного елемента став порожнім.
Код повернуто назад, тест знову зелений (`OK`, 5 тестів).

### Підрахунок вартості прогону в токенах і доларах

Вже реалізовано в `core/cost.py` + `core/agent.py:USAGE` — рахує токени по кожній
моделі окремо і переводить у долари за реальними цінами. Приклад з реального прогону
(happy path, ланцюжок з двох інструментів):

```
outcome: ok · calls: 3 · in: 4307 · out: 456
usd: 0.019761
```

`run.py` виводить це після кожного прогону разом з економією від каскаду моделей
(`cost.savings_vs_single_model`).

### Жорсткий ліміт бюджету

Новий `MAX_COST_USD` у `config.py` (за замовчуванням `$0.05` — з запасом понад
реальний happy-path прогін у ~$0.02, але не нескінченний). У `core/agent.py` вартість
накопичується на кожному кроці циклу; якщо перевищено — цикл зупиняється з новим
`outcome: "budget_exceeded"`, а не мовчки продовжує витрачати.

Перевірено на реальному API з навмисно заниженим лімітом (`MAX_COST_USD=0.008`,
менше вартості навіть одного виклику з великим контекстом):

```
outcome: budget_exceeded
spent_usd: 0.011196
turns: 2
  get_order_status({'tracking': 'EE123456789UA'}) -> {...'days_in_transit': 15...}
ескалація: перевищено ліміт вартості обробки
відповідь: Досягнуто ліміту вартості обробки ($0.01). Передаю звернення оператору.
```
