# Как устроен RAG в module2 — разбор реализации

Это разбор конкретного кода в `module2/`, а не общая теория RAG. Цель — чтобы
ты мог взять паттерны отсюда и построить свою систему, понимая, зачем
каждый слой существует и какую проблему решает.

## 1. Общая картина

Модуль строится вокруг одного and того же сценария: агент поддержки почтового
оператора. У него есть:

- **цикл агента** (`core/agent.py`) — общий для всех модулей курса, не меняется;
- **инструменты бэкенда** (`domain/backend.py`) — фейковый API (статус посылки,
  право на возврат, создание претензии);
- **слой знаний** (`domain/knowledge.py` и его более продвинутые версии) —
  это и есть RAG: правила и тарифы, которые агент не должен выдумывать, а
  обязан цитировать.

Ключевая идея всего модуля: **RAG — это не более чем функция, которая
возвращает релевантный текст по запросу**, и её реализация может меняться
(лексика → эмбединги → векторная БД → agentic), а интерфейс — `retrieve()` /
`as_context()` — остаётся одним и тем же. Агент вообще не знает, что стоит
за этим слоем.

Файлы делятся на две группы:

| Группа | Файлы | Что показывает |
|---|---|---|
| **Static RAG** (baseline) | `domain/knowledge.py`, `knowledge_vec.py`, `knowledge_qdrant.py` | как эволюционирует retriever: лексика → эмбединги → векторная БД |
| **Продвинутые паттерны** | `chunking.py`, `self_rag.py`, `rag_agentic.py`, `ragas_compare.py` | чанкинг, ворота качества, agentic retrieval, измерение |

## 2. Ядро агента: `core/agent.py`

Это НЕ RAG-код, но важно понимать, потому что весь RAG подключается именно
сюда. Обычный tool-use цикл Anthropic API:

```
run_agent(system, tools, query):
    messages = [user query]
    loop до MAX_TURNS:
        resp = client.messages.create(system=system, tools=tools, messages=messages)
        если resp.stop_reason != "tool_use":
            → это финальный ответ, возвращаем
        иначе:
            выполняем все tool_use блоки через dispatch()
            добавляем assistant-turn и tool_result в messages
    если вышли из цикла по лимиту шагов → turns_exhausted
```

Важные детали:

- **`system` — это просто строка.** Самый простой способ добавить RAG в
  агента — это дописать в неё найденный контекст. Именно так работает
  static RAG (см. ниже).
- **Ретраи на 429/500/529** с экспоненциальным бэкоффом (`_call`).
- **Каскад моделей**: `MODEL` (дорогая, `claude-sonnet-4-6`) — для цикла
  агента, `MODEL_FAST` (дешёвая, `claude-haiku-4-5`) — для вспомогательных
  вызовов вроде классификации, grade, rewrite (см. `ask()` в этом же файле).
  Это важно для RAG-паттернов из `self_rag.py` — там LLM-судья и rewrite
  всегда идут через дешёвую модель.
- **`ask()` / `ask_json()`** — вызов без инструментов, для одноразовых
  классификаций/оценок. `self_rag.py` использует `ask()` для grade и rewrite.

## 3. Инструменты бэкенда: `domain/backend.py`

Фейковый API поштового оператора: `get_order_status`, `check_refund_eligibility`,
`check_compensation`, `create_claim`, `escalate_to_human`. Каждый инструмент —
обычная Python-функция + JSON-схема (`_schema()`) для Anthropic tool-use.
`tools_for(module_number)` возвращает набор инструментов, доступных на
данном этапе курса (`CAPABILITIES` — словарь module → список имён).

Это не RAG, но полезная деталь: **`domain/backend.py` — источник фактов о
конкретном заказе, а `domain/knowledge.py` — источник правил.** RAG отвечает
за вторую категорию. `ragas_compare.py` явно подсвечивает эту границу (см.
раздел 9 — про faithfulness).

## 4. Простейший RAG (baseline): `domain/knowledge.py`

Это стартовая точка — RAG без какой-либо инфраструктуры, чтобы проект
запускался вообще без установки чего-либо тяжёлого.

```python
KB = [
    ("повернення доставка прострочення строк кошти гроші",   # ключевые слова
     "Правило 4.2. Якщо фактичний строк доставки перевищує заявлений на 5 і більше днів…"),
    ...
]

def retrieve(query, k=3):
    words = set(query.lower().split())
    for keys, text in KB:
        exact = len(words & set(keys.split()))      # точное совпадение слов
        partial = ...                                 # префиксное совпадение (5 символов)
        score = exact*2 + partial
    → сортировка по score, топ-k, где score > 0
    → если ничего не нашлось — fail-open: отдаёт лучший (пусть и нерелевантный) результат
```

Три момента, которые стоит унести в свою реализацию:

1. **KB — это список пар `(ключевые_слова, текст_правила)`.** Ключевые слова
   вручную подобраны как «синонимический якорь» — это костыль, который
   лексический поиск (BM25-подобный) не умеет обходить сам. Именно на этом
   и ломается лексика (раздел 5).
2. **`retrieve()` и `as_context()` — это весь публичный интерфейс.**
   `as_context(query)` просто оборачивает `retrieve()` в текстовый блок,
   готовый к вставке в system-промпт:
   ```python
   def as_context(query, k=3):
       return "\n\nВитяг з бази знань:\n" + "\n---\n".join(retrieve(query, k))
   ```
3. **fail-open vs fail-closed.** Здесь при пустом результате возвращается
   "наименее нерелевантное" правило (`hits or [scored[0][1]]`) — это
   осознанно плохое поведение, README прямо ставит вопрос «что хуже: пустой
   контекст или ложное правило?». `knowledge_vec.py` и `knowledge_qdrant.py`
   выбирают fail-closed (пустой контекст лучше галлюцинации).

### Как RAG подключается к агенту: `modules/m01_core.py` vs `modules/m02_rag.py`

Разница — буквально одна строка:

```python
# m01_core.py — БЕЗ базы знаний
result = run_agent(system=BASE_PROMPT, tools=tools_for(1), query=query)

# m02_rag.py — С базой знаний
result = run_agent(system=BASE_PROMPT + as_context(query), tools=tools_for(2), query=query)
```

Это и есть самый минимальный RAG: **retrieval выполняется один раз до вызова
модели, безусловно, и подмешивается в system prompt.** Модель сама решает,
использовать ли эти правила или нет (но обычно использует, потому что они
там есть).

## 5. Векторный retriever: `knowledge_vec.py`

Показывает, где лексика (раздел 4) ломается, и чем это лечится.

**Проблема:** запрос «кур'єр загубив мій пакунок» не матчит KB-запись
«втрачено» — лексика (даже с префиксным сравнением) не видит семантической
близости «загубив» ≈ «втрачено».

**Решение — эмбединги + косинусное сходство:**

```python
def _embed(texts, kind):  # kind: "query" | "passage"
    если есть OPENAI_API_KEY → OpenAI text-embedding-3-small
    иначе → sentence-transformers, локальная intfloat/multilingual-e5-small

def _cos(a, b):  # ручная реализация косинусного сходства, без numpy
    dot(a,b) / (|a| * |b|)

_index = None  # ленивая индексация: embed() всей KB один раз при первом вызове

def retrieve(query, k=3):
    _ensure_index()
    q = _embed([query], "query")[0]
    scored = sorted по _cos(q, v) для каждого вектора в индексе
    return [text for score, text in scored[:k] if score >= _THRESHOLD]  # fail-closed
```

Ключевые архитектурные детали:

- **e5-модели требуют префиксов `"query: "` / `"passage: "`** перед текстом —
  это часть их обучающего протокола, без этого качество проседает. Если
  будешь использовать e5/multilingual-e5, не забудь про это.
- **Порог (`_THRESHOLD`) разный для разных бэкендов** (0.25 для OpenAI,
  0.78 для e5) — косинусы у разных моделей имеют разное распределение,
  порог нельзя переносить между моделями не глядя.
- **`_THRESHOLD` — это fail-closed граница**: если top-score ниже порога,
  `retrieve()` возвращает `[]`, и `as_context()` отдаёт пустую строку вместо
  «хоть что-то». Порог подбирается эмпирически на реальных данных
  (README прямо говорит: «поріг тюниться на даних, не береться з
  підручника» — разница между верным и неверным совпадением была 0.013).
- **Индекс — просто список `(vector, text)` в памяти**, полный перебор
  (`O(n)` на запрос). Это нормально для 14 записей и демонстрации; в проде
  это заменяется на ANN-индекс — см. следующий раздел.

## 6. Векторная БД: `knowledge_qdrant.py`

Тот же retriever, но в Qdrant, с сохранением **того же интерфейса**
(`retrieve()` / `as_context()`) — агент опять не видит разницы.

Что добавляется по сравнению с in-memory списком:

```python
def client():
    url = os.getenv("QDRANT_URL")
    QdrantClient(url=url) if url else QdrantClient(":memory:")   # embedded-режим без Docker
    _ensure_collection(...)                                       # ленивая индексация коллекции

def retrieve(query, k=3, topic=None):
    flt = Filter(must=[FieldCondition(key="topic", match=MatchValue(value=topic))]) if topic else None
    hits = client().query_points(COLLECTION, query=embed(query), limit=k,
                                  query_filter=flt, score_threshold=THRESHOLD)  # fail-closed на уровне БД
    return [h.payload["text"] for h in hits]
```

- **payload** — метаданные рядом с вектором (`text`, `keys`, `topic`).
  `topic` вычисляется грубым эвристическим маппингом ключевых слов
  (`_topic()`) — просто чтобы было по чему фильтровать.
- **`score_threshold` передаётся прямо в БД** — fail-closed теперь на уровне
  движка поиска, а не постфактум в Python.
- **`:memory:` режим Qdrant** — embedded-инстанс внутри процесса, без
  Docker. Полезный трюк для дев-окружения/тестов: `QdrantClient(":memory:")`.
- Если задать `QDRANT_URL` — переключается на реальный сервер без изменения
  кода.

Вывод раздела: путь эволюции retriever'а — **список строк → лексический
скоринг → эмбединги в памяти → эмбединги в векторной БД с фильтрами** — и
каждый шаг ничего не меняет в контракте `retrieve()`/`as_context()`. Это
главный архитектурный урок: **отделяй интерфейс retrieval'а от его
реализации с первого дня**, тогда сможешь менять бэкенд без переписывания
агента.

## 7. Чанкинг: `chunking.py`

В этой KB чанкинг не нужен (каждое правило — уже атомарный чанк ~40
токенов), поэтому файл — отдельная демонстрация на синтетическом документе
(«Розділ 4…7» — цельный текст условий), а не часть реального pipeline.

```python
def chunk(text, size, overlap):
    per_chunk = size / 1.3    # ~1.3 токена на слово для укр. текста
    step = (size - overlap) / 1.3
    for start in range(0, len(words), step):
        yield words[start : start+per_chunk]
```

Простейший чанкер «по словам с фиксированным перекрытием». Демонстрирует
компромисс:

- **малый чанк** → факт отрывается от условия (например, сумма «120 грн»
  оказывается в одном чанке, а условие «5 і більше днів» — в соседнем);
- **большой чанк** → в промпт уезжает много лишнего, релевантное тонет;
- **overlap** — страховка: соседние чанки частично повторяются, поэтому факт
  на границе попадает в оба. `--compare` явно показывает: при 60 токенах без
  overlap связанные факты рвутся, при overlap=18 — остаются вместе, при этом
  число чанков не меняется.

Если у тебя источник знаний — не список готовых правил, а цельный документ
(PDF, Confluence, транскрипт), тебе нужен именно этот шаг перед индексацией.

## 8. Ворота качества: `self_rag.py` (Self-RAG / CRAG паттерн)

Идея: **между retrieval и генерацией стоит проверка**, которая решает, что
делать, если найденного недостаточно — вместо того, чтобы дать модели
галлюцинировать поверх слабого контекста.

Два уровня ворот, от дешёвого к дорогому:

```
1. ПОРОГ (детерминированный, $0)
   score < threshold → считаем, что не нашли (уже встроено в knowledge_vec.retrieve)

2. LLM-GRADE (дешёвая модель, ~100 токенов)
   схожесть может быть высокой, но контекст всё равно не отвечает на вопрос.
   Спрашиваем модель: RELEVANT или WEAK.
```

Код:

```python
def grade(ctx, query, use_llm=True):
    if not ctx: return "WEAK"                    # порог уже всё отсеял
    if not use_llm: return "RELEVANT"             # уровень 1: доверяем порогу
    verdict = ask(GRADE_PROMPT, f"Питання: {query}\n\nВитяг:\n{ctx}", max_tokens=10)
    return "WEAK" if "WEAK" in verdict.upper() else "RELEVANT"

def answer_with_gate(query, use_llm=True):
    ctx = retrieve(query, k=3)
    verdict = grade(ctx, query, use_llm)
    if verdict == "WEAK":
        better = ask(REWRITE_PROMPT, query, max_tokens=40)   # CRAG: переформулировать запрос
        ctx2 = retrieve(better, k=3)
        if ctx2 and grade(ctx2, query, use_llm) == "RELEVANT":
            ctx, verdict = ctx2, "RELEVANT (після rewrite)"
        else:
            → эскалация на человека (escalate_to_human)
    return собранный ответ с трассировкой шагов
```

Это то, что в литературе называют **Self-RAG / CRAG** (Corrective RAG):

- **CRAG-часть здесь** — при WEAK-вердикте запрос переформулируется языком
  предметной области (`REWRITE`-промпт явно перечисляет термины: «прострочення,
  компенсація, розшук, вкладення») и делается повторный поиск.
- Если и после rewrite ничего толкового не нашлось — **явная эскалация**
  (`escalate_to_human`), а не попытка ответить вслепую.

Практический вывод: **никогда не полагайся только на порог схожести** —
он ловит семантически далёкие запросы, но не ловит случай «похоже, но не
отвечает на вопрос». LLM-grade — это второй, более дорогой, но более точный
фильтр. Комбинация «дешёвый детерминированный фильтр → дорогой LLM-фильтр →
исправление → эскалация» — общий паттерн, который стоит копировать.

## 9. Agentic RAG: `rag_agentic.py`

Static RAG (раздел 4) делает **один retrieval на весь запрос, безусловно**,
до вызова модели. Agentic RAG превращает retrieval в **инструмент**, который
модель вызывает сама, сколько раз нужно, с любыми формулировками запроса.

```python
def _search_kb(query: str) -> dict:
    hits = retrieve(query, k=3)
    return {"rules": hits} if hits else {"rules": [], "note": "нічого не знайдено"}

SEARCH_KB_SCHEMA = {
    "name": "search_kb",
    "description": "Шукає правила й тарифи... Викликай перед будь-яким твердженням про правила чи суми.",
    "input_schema": {"properties": {"query": {"type": "string"}}, "required": ["query"]},
}

def run_agentic(query):
    backend.IMPL["search_kb"] = _search_kb          # регистрируем в общем dispatch()
    tools = backend.tools_for(2) + [SEARCH_KB_SCHEMA]
    result = run_agent(
        system=BASE_PROMPT + " Правила бери ТІЛЬКИ з search_kb — не вигадуй.",
        tools=tools, query=query,
    )
    result["kb_searches"] = [t["input"]["query"] for t in result["trace"] if t["tool"] == "search_kb"]
    return result
```

Механика простая: `retrieve()` из `domain/knowledge.py` оборачивается в
обычный tool (такой же, как `get_order_status` и другие) и регистрируется в
том же `IMPL`-диспетчере, который уже используют инструменты бэкенда
(`domain/backend.dispatch`). Дальше это просто ещё один инструмент в общем
tool-use цикле `core/agent.run_agent` — никакой отдельной инфраструктуры не
нужно.

**Где это выигрывает:** на составном запросе («Посилка у розшуку два місяці.
Що належить за вміст і скільки чекати виплату?») модель сама делает
**несколько разных поисков** — например, «компенсація за втрачене
відправлення розшук» и отдельно «строк виплати компенсації після завершення
розшуку». Static RAG сделал бы один top-K по всему запросу и упустил бы
часть аспектов. Цена — лишние вызовы модели и задержка, поэтому на простых
запросах agentic RAG избыточен.

## 10. Оценка: `ragas_compare.py`

Сравнивает три конфигурации на 6 вопросах (RAGAS-метрики):

```python
VARIANTS = {
    "lexical":        run_lexical,         # domain/knowledge.py (static)
    "vector":         run_vector,          # knowledge_vec.py (static)
    "agentic-vector":  run_agentic_vector,  # search_kb как tool поверх векторного retriever'а
}
```

Метрики: `faithfulness` (спирается ли ответ на выданный контекст),
`answer_relevancy` (отвечает ли на вопрос), `context_recall` (нашёл ли
retriever то, что нужно — главная метрика для сравнения retriever'ов между
собой).

Важная ловушка, явно описанная в коде и README:

```python
def _tool_facts(result):
    """Виводи інструментів — теж контекст, який бачив агент.
    Якщо давати Ragas лише правила з БЗ, faithfulness провалюється на
    фактах з бекенду (статус, дні, суми) — вони «не підтверджені
    контекстом», хоча агент їх не вигадав."""
    return [f"Дані бекенду ({t['tool']}): {json.dumps(t['output'])}"
            for t in result["trace"] if t["tool"] != "search_kb"]
```

**Если ты меряешь RAG-качество через RAGAS/подобные инструменты — клади в
`contexts` абсолютно всё, что модель реально видела**, включая выводы других
инструментов (статус посылки, суммы), а не только записи из базы знаний.
Иначе faithfulness будет ложно низким — модель накажут за использование
фактов, которые она честно получила через другой tool.

## 11. Что унести в свою реализацию — чеклист

1. **Разделяй интерфейс и реализацию retrieval'а с первого дня.**
   `retrieve(query, k) -> list[str]` и `as_context(query) -> str` — весь
   контракт. Всё остальное (лексика, эмбединги, векторная БД, фильтры)
   меняется под капотом без переписывания агента.
2. **Fail-closed по умолчанию.** Пустой результат при отсутствии
   уверенного совпадения — лучше, чем подсунуть модели нерелевантный текст,
   на основе которого она сгенерирует правдоподобную, но неверную
   галлюцинацию. Держи порог явным и настраиваемым, подбирай его на
   реальных запросах, а не «по учебнику».
3. **Static RAG — это стартовая точка, не финал.** Один retrieval на весь
   запрос — просто, дёшево, но проваливается на составных вопросах.
   Agentic RAG (`retrieve` как обычный tool) даёт модели решать, сколько раз
   и с какими формулировками искать — почти бесплатно добавляется поверх
   существующего tool-use цикла.
4. **Ставь ворота между retrieval и генерацией**, если цена ошибки высокая:
   детерминированный порог (дёшево) → LLM-grade (дороже, но ловит
   «похоже, но не отвечает на вопрос») → rewrite-and-retry (CRAG) →
   эскалация как последний рубеж. Никогда не давай модели молчаливо
   выдумывать при пустом/слабом контексте.
5. **Чанкинг нужен только когда источник — цельный документ.** Если твоя
   база знаний уже состоит из атомарных записей (FAQ-пункты, короткие
   правила), не усложняй — чанкинг с overlap решает проблему, которой у
   тебя может не быть.
6. **Если меряешь качество (RAGAS или свои метрики) — в контекст должно
   попасть всё, что видела модель**, включая выводы других инструментов,
   а не только retrieval-хиты. Иначе метрики будут врать в невыгодную
   сторону.
7. **Каскад моделей.** Дорогая модель — только для основного цикла
   рассуждений агента. Роутинг, grade, rewrite, judge — дешёвая модель с
   `temperature=0` (детерминированность важна, когда это судья/гейт).
