# module2Lawyer — юридичний асистент з RAG

Навчальний проєкт: AI-агент (доступний через Telegram-бота), що консультує
з питань права України, спираючись **лише** на поточний текст
відслідковуваних документів, а не на власні (можливо застарілі чи
вигадані) знання моделі.

Побудований поетапно, за зразком `module2` цього ж репозиторію — від
найпростішого лексичного пошуку до agentic RAG, автоматичної оцінки якості
й щоденного відстеження нових редакцій законів.

> Це навчальний прототип, а не офіційна юридична консультація. Закони
> змінюються — перед тим як покладатися на відповідь у реальній ситуації,
> звіряйте з актуальною редакцією на zakon.rada.gov.ua.

## Джерело даних: офіційний OpenData API

Текст тягнеться з **офіційного Порталу відкритих даних Верховної Ради**
(`data.rada.gov.ua`), а не скрапінгом людського сайту zakon.rada.gov.ua —
той для ботів закритий власним `robots.txt` (`Disallow: /` для всіх, крім
кількох іменованих). API — санкціонований, задокументований самим
порталом канал (`/ogd/zak/laws/readme.txt`), дані відкриті для вільного
використання й поширення (з посиланням на джерело).

Обов'язкова умова доступу — заголовок `User-Agent`, що **дослівно**
дорівнює `OpenData`. Рекомендована пауза між запитами — 5-7с; у
`crawler.py` вона вбудована автоматично (`_pace()`), окремо чекати ніде
не треба.

```
data.rada.gov.ua/laws/show/{id}       — повний текст поточної редакції
data.rada.gov.ua/laws/card/{id}.json  — картка: статус, дати, номер акта,
                                        повна історія редакцій (eds)
```

**Резервний варіант** — `pdf_source.py`: якщо API колись стане
недоступний, є робочий шлях назад до ручних PDF у `pdf/` (той самий
контракт `fetch_clauses(doc)`). Зараз не використовується; щоб
переключитися — замінити імпорт у `ingest.py` (`from crawler import
fetch_clauses` → `from pdf_source import fetch_clauses`) і покласти
актуальний PDF у `pdf/`.

## Встановлення

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env      # і впишіть ANTHROPIC_API_KEY
```

Важкий eval-стек (ragas) — окремо, лише для `eval.py`:

```bash
pip install -r requirements-eval.txt
```

Перед першим запуском — один раз проіндексувати документи:

```bash
python ingest.py
```

Тягне поточний текст усіх `crawler.TRACKED` документів, ріже на чанки за
юридичною структурою, рахує ембединги (локальна модель, без API-ключа) і
зберігає у два місця:

- `qdrant_data/` — векторний індекс (персистентний локальний Qdrant, диск, не `:memory:`)
- `laws.db` — нормалізована SQLite: `documents` (номер акта, дати, статус,
  підстава редакції, URL) і `clauses` (кожен абзац окремо, з точним
  якорем на сайт)

Заново індексувати (усі документи разом — див. «Нюанси» про точкове
оновлення) —

```bash
python ingest.py --reset
```

— або дочекатися сповіщення від `watch.py`/бота: щодня перевіряє дату
редакції й підказує, коли час це зробити.

## Що є і навіщо

| Файл | Що робить |
|---|---|
| `config.py` | ключ, моделі (основна + дешева), персона агента |
| `core/agent.py` | `ask()` — один виклик моделі; `run_agent()` — tool-use цикл для agentic |
| `core/cost.py` | ціни моделей → $ з `core.agent.USAGE["by_model"]`, для `/usage` у боті |
| `domain/knowledge.py` | лексичний retriever, **11 ручних пунктів** (baseline, лише ПДР+поліція) |
| `crawler.py` | OpenData API → статус/картка + повний текст → клаузи за структурою |
| `pdf_source.py` | резервне джерело (PDF), той самий контракт, зараз не використовується |
| `db.py` | SQLite: `documents` (номер, дати, статус) + `clauses` (абзаци, якорі) |
| `ingest.py` | crawler → чанки згруповані за частиною/пунктом → ембединги → Qdrant + SQLite |
| `knowledge_qdrant.py` | векторний retriever — **увесь текст** усіх документів, з точною цитатою |
| `watch.py` | щоденна перевірка дати редакції проти того, що в SQLite |
| `verify.py` | перевірка повноти індексації (пропуски в нумерації статей/розділів) — без мережі |
| `run.py` | порівняння: без бази / лексика / вектор |
| `self_rag.py` | Self-RAG / CRAG: поріг → LLM-grade → rewrite → ескалація |
| `rag_agentic.py` | retrieval як інструмент `search_kb`, модель шукає сама |
| `eval.py` | Ragas: faithfulness / relevancy / context_recall на 4 конфігураціях |
| `router.py` | класифікатор просте/складене — self_rag чи agentic, fallback на ескалації |
| `bot.py` | Telegram-бот поверх `router.answer()` + щоденний watch.py |

Усі retriever'и (`domain/knowledge.py`, `knowledge_qdrant.py`) реалізують
той самий контракт — `retrieve(query, k) -> list[str]` і
`as_context(query, k) -> str`. Агент (`core/agent.py`, `run.py`,
`self_rag.py`, `rag_agentic.py`) не знає і не має знати, що саме за цим
контрактом — лексика чи векторна БД.

- `code` — Розділ (**римські** цифри) → [Глава, не завжди є] → Стаття →

розмітку (`crawler.fetch_clauses`) на цьому документі окремо, **до**
того, як довіряти парсеру масштаб: дивись розділ нижче про реальні баги,
знайдені саме так.

## Telegram-бот

```bash
# 1. отримати токен: у Telegram написати @BotFather → /newbot → скопіювати токен
# 2. вписати TELEGRAM_BOT_TOKEN у .env
# 3. переконатися, що індекс уже зібраний (python ingest.py)
python bot.py
```

Бот відповідає через `router.answer()` — дешевий класифікатор
(`MODEL_FAST`) визначає, просте питання чи складене (кілька різних
аспектів одночасно), і вибирає конвеєр: просте → `self_rag.py` (1-2
виклики моделі, швидко й дешево), складене → одразу `rag_agentic.py`
(модель сама шукає, скільки треба). Якщо класифікатор помилився і
self_rag усе одно ескалював — `router.py` не віддає людині відмову
одразу, а пробує agentic як останню спробу перш ніж чесно здатися.
Причина цієї архітектури й реальний приклад «до/після» — у розділі
нижче. Long polling: процес просто має бути запущений і мати доступ до
інтернету, публічний HTTPS-сервер не потрібен.

Синхронний виклик `router.answer()` виконується в окремому потоці
(`run_in_executor`), щоб не блокувати обробку інших повідомлень.
Кілька послідовних викликів моделі (кожен пошук — окремий turn) можуть
розтягнути відповідь на 5-30+ секунд — індикатор «друкує…» оновлюється
кожні 4с окремою задачею (`bot._keep_typing`), інакше Telegram гасить
його вже за ~5с. Пам'яті між повідомленнями немає — кожне питання
обробляється незалежно (діалоговий контекст — це модуль 4 курсу, не тут).

**`/usage` — витрати в токенах і доларах.** Лише для `ADMIN_CHAT_ID`, якщо
заданий (інакше доступно будь-кому, хто напише боту). Рахує з моменту
запуску процесу (`core/agent.USAGE`, скидається на кожен рестарт pm2) — з
розбивкою по моделі окремо, бо `MODEL`/`MODEL_FAST` мають різну ціну
(`core/cost.py`). Реальний вивід на одне просте питання:

```
Витрати з моменту запуску процесу (31.08.2026 14:23):

claude-sonnet-4-6
  викликів: 1  вх: 2013  вих: 184  $0.0088
claude-haiku-4-5-20251001
  викликів: 2  вх: 1997  вих: 11  $0.0021

Усього: 3 викликів, 4010+195 токенів, $0.0109
```

**Щоденна перевірка оновлень.** Якщо задано `ADMIN_CHAT_ID` у `.env`, бот
раз на день (09:00 за часом сервера) перевіряє дату поточної редакції
кожного відслідковуваного документа і, якщо вона змінилася, шле
повідомлення з посиланням:

```
Вийшла нова редакція: «Кримінальний кодекс України»
15.04.2026 → 20.05.2026
https://zakon.rada.gov.ua/laws/show/2341-14

Щоб оновити базу знань бота:  python ingest.py --reset
```

Свідомо лише сповіщає, не переіндексовує сам — юридичний текст вартий
перегляду людиною перед тим, як міняти базу знань агента. Перевірити
вручну, без очікування 09:00: `python watch.py`.

## Перевірка повноти індексації

```bash
python verify.py
```

Рахує клаузи в `laws.db` і шукає пропуски в нумерації статей/розділів —
якщо реальна структура 1, 2, 3, 5 (без 4), це підозріло: або парсер не
впізнав заголовок і склеїв його із сусіднім, або статтю справді
законно виключили. **Обидва випадки трапилися насправді** під час
розробки — і їх варто розрізняти вручну (глянути реальний текст на
сайті), а не довіряти висновку автоматично.

### Реальні баги, знайдені цим інструментом (і виправлені)

1. **Зайвий символ у кінці заголовка розділу.** ПДР: «28. РУХ ПО
   ГІРСЬКИХ ДОРОГАХ...**\***» закінчувався зноскою (`*`); строгий `$` у
   кінці регексу цього не пробачав, і весь розділ 28 мовчки приклеївся
   до розділу 27.
2. **Пробіл перед крапкою в номері статті.** Кримінальний кодекс:
   «Стаття 168 . Розголошення...» (пробіл перед `.`) — регекс очікував
   крапку одразу після цифр, стаття 168 приклеїлась до 167.
3. **Кирилиця замішана в «римських» цифрах розділу.** КПК: «Розділ
   VІ» — де останній символ це не латинська `I`, а **кирилична `І`**
   (U+0406, візуально нерозрізнима). Через це чотири розділи КПК (2, 6,
   7, 8) не розпізнавались і губилися в сусідніх. Найнеприємніший з
   трьох — його неможливо помітити, просто дивлячись на текст.
4. **Заголовки суцільно ВЕЛИКИМИ.** Податковий кодекс пише «РОЗДІЛ I.»
   замість «Розділ I.» — регекс був чутливий до регістру, жоден розділ
   ПК не розпізнавався. Виправлено `re.IGNORECASE` на всіх ключових
   словах структури (Розділ/Глава/Стаття).
5. **«Глава» римськими цифрами замість арабських, без окремого
   Розділу.** КЗпП: «Глава I» — деякі кодекси не мають рівня Розділ
   узагалі, і Глава там нумерується як розділ в інших документах.

### Втрата чинності — знайдено вручну, тепер перевіряється автоматично

Під час партії 2 виявилось: **Господарський кодекс України (436-15)
втратив чинність 28.08.2025**, а **Житловий кодекс (5464-10) — «втратив
чинність крім окремих положень»**. Обидва мали `status_code` (з
`card.json`), відмінний від `5` (чинний) — усі інші 25 документів мають
рівно `5`. Обидва прибрано з `TRACKED`.

`ingest.py` тепер сам перевіряє `status_code` кожного документа перед
індексацією і пропускає (з попередженням у консоль) усе, що не `5` —
ця помилка не повинна повторитися мовчки на наступних партіях.

### Пропуски, які виявились ЛЕГІТИМНИМИ (не баг)

Перевірено вручну на реальному тексті — старі, часто редаговані кодекси
регулярно офіційно «виключають» статті/розділи цілими шматками, залишаючи
постійні дірки в нумерації:

- Конституція, ст. 121-123 (Розділ VII «Прокуратура») —
  **виключено Законом № 1401-VIII від 02.06.2016**
- ККУ, ст. 234-235 — **виключено Законом № 4025-VI від 15.11.2011**
- КПК, ст. 444-458 (уся Глава 33) — **виключено Законом № 2147-VIII від 03.10.2017**
- Податковий кодекс, розділи 7, 10, 11, 13, 15-17 (плата за землю, збір
  за радіочастотний ресурс тощо) — виключені окремими податковими
  реформами різних років
- Про державну службу, Про господарські товариства та інші — той самий
  патерн підтвердився ще на 3+ документах партій 4-5

### Виправлено: цитований текст поправок до ІНШОГО закону

Реальний випадок партії 6: **Про Державний земельний кадастр** показував
статті аж до №204, хоча власних у документі ~41. Причина — прикінцеві
положення містять дослівний текст статей **ІНШОГО закону** (Земельного
кодексу), який цей закон вставляє туди поправкою («доповнити Земельний
кодекс статтею 204 такого змісту: ...»). Той самий патерн — і в Про
акціонерні товариства (вставка в закон про ТОВ/ТДВ, до ст. 162 замість
власних ~137). Структурно (HTML) ці абзаци нічим не відрізняються від
справжніх заголовків — окремого маркера чи лапок у `get_text()` немає.

**Фікс:** `_FINAL_PROVISIONS_RE` у `crawler.py` шукає заголовок
«Прикінцеві (та перехідні) положення» (окремим `Розділ`, або як назва
самої останньої статті — обидва варіанти трапляються). Після нього
`article`/`section` більше не оновлюються за новими «Стаття N.» —
далі йде лише нумерація частин/пунктів у межах цього розділу. Обидва
реальні випадки після фіксу показують коректну верхню межу (41 і 137
відповідно). Не 100% гарантія на всі можливі формулювання цього
заголовка, але покриває стандартну (найпоширенішу) редакційну практику.

Висновок: `verify.py` — інструмент для звуження кола підозрюваних, а не
остаточний вердикт. Кожен знайдений пропуск вартий одного погляду на
реальний текст, перш ніж вважати його багом чи фактом.

### Виправлено: хибне спрацювання детектора «Прикінцевих положень»

Реальний випадок партії 22: **Про ветеринарну медицину та благополуччя
тварин** (1206-20) показував **0 статей** — увесь документ (2397 клауз)
пройшов повз розмітку. Причина: перед самим Розділом I у документі стоїть
редакційна виноска-примітка — `«{У тексті Закону (крім розділу XV
"Прикінцеві та перехідні положення"): ...}»` — яка просто ЗГАДУЄ назву
цього розділу в дужках, пояснюючи межі дії іншої правки. `_FINAL_PROVISIONS_RE`
використовував `search()` (пошук фрази будь-де в абзаці) і коротку межу
довжини (`<100` символів) — цей запис під межу підпадав і викликав
`in_final = True` на самому початку документа, до першої реальної
«Стаття 1.». Раз увімкнувшись, цей стан більше не скидається (свідомий
дизайн — щоб не плутати чужі «Стаття N.» з прикінцевих із власними
статтями документа, див. вище) — тож усі 95 реальних статей до кінця
документа лишились нерозпізнаними.

**Фікс:** регекс заякорено на початку рядка (`^`, `match()` замість
`search()`) і дозволяє лише короткий префікс-заголовок — необов'язкове
слово «Розділ»/«Стаття» + номер, і одразу «Прикінцеві...». Текст, який
ЗГАДУЄ фразу посеред речення (як ця виноска, що починається з `{`), більше
не збігається. Обидва реальні випадки заголовків («Розділ VII ПРИКІНЦЕВІ...»
і «Стаття 13. Прикінцеві...») продовжують спрацьовувати як і раніше.
Після фіксу документ показує коректні 95 статей (1..95).

### k=3 → k=6: recall падав із ростом корпусу

Два реальних випадки під час партії 3: питання про НАБУ (директор — ст. 7)
і про ЦКУ (позовна давність — ст. 257) отримували `WEAK` і чесну відмову,

Підняли `k` за замовчуванням до 6 у `knowledge_qdrant.py`,

випадки після цього відповідають точно. Якщо корпус ще зросте і k=6
перестане вистачати — наступний крок не "ще більший k" (розмиває
контекст), а hybrid search (BM25 + вектор, Qdrant підтримує sparse
вектори нативно) або reranker.

## Еволюція retriever'а (як і в module2)

1. **Лексика** (`domain/knowledge.py`) — 11 пунктів вписані вручну, збіг
   слів + префіксне співпадіння. Швидко зрозуміти, як усе працює, але
   ламається на синонімах і покриває лише ПДР+поліцію.
2. **Вектор** (`crawler.py` + `ingest.py` + `knowledge_qdrant.py`) — весь
   поточний текст 6 документів, отриманий з офіційного API (5372 чанки,
   згруповані за частиною статті чи пунктом розділу — щоб перелік підстав
   приходив цілим списком, а не розсипався на випадкові 1-3 пункти).
   Кожна цитата в контексті — реконструйована з metadata («ККУ, ст. 185,
   ч. 1»), а не вирізана регексом із суцільного тексту, і веде на точний
   абзац на сайті (`#nXXX`).
3. **Self-RAG / CRAG ворота** (`self_rag.py`) — векторний поріг ловить
   лише зовсім нерелевантне; LLM-grade ловить випадок «схоже, але не по
   суті». На WEAK — переформулювати запит мовою закону і шукати ще раз;
   якщо й тоді порожньо — чесна відмова замість вигаданої статті.
4. **Agentic** (`rag_agentic.py`) — пошук стає інструментом `search_kb`.
   На складеному питанні модель сама робить кілька різних пошуків замість
   одного розмитого.

## Реальний кейс: чому self_rag ескалює, а agentic — відповідає

Живий приклад від користувача бота (не тестове питання з `QUERIES`):

> «Я іхав на своїй машині по місту 73 км на годину і мене зупинили і
> кажуть що я перевищів швидкість але не показують докази з камери яка
> фіксує швидкість»

`self_rag.answer_with_gate()` (те, що реально стоїть за ботом) — ескалація:

```
retrieve → 6 витягів
grade → WEAK
rewrite → «Оскарження постанови про порушення ліміту швидкості без доказів.» → 6 витягів
ескалація → людині
→ На жаль, у проіндексованих джерелах я не знайшов відповіді на це
питання навіть після переформулювання запиту. Радимо звернутися до
практикуючого юриста...
```

Очікування користувача (сформульовано до діагностики): агент мав би
подивитися, яка максимальна швидкість дозволена в місті, уточнити, чи
були обмежувальні дорожні знаки, і сказати, наприклад, що на прилад
фіксації потрібен сертифікат, а сам прилад має стояти на штативі, а не в
руках — і дати посилання на конкретну норму.

**Діагностика.** Пряме звернення до `knowledge_qdrant.retrieve()` в обхід
воріт показало: потрібні норми **є** в базі — «Стаття 122» КУпАП
(перевищення швидкості), «Стаття 14» КУпАП (відповідальність за
порушення, зафіксовані в автоматичному режимі), «Стаття 258» КУпАП
(коли протокол не складається — саме про автоматичну фіксацію), «Стаття
171» КУпАП (повірка засобів вимірювальної техніки), п. 12.4 ПДР (50
км/год у населеному пункті), ст. 40 Закону «Про Національну поліцію»
(застосування технічних приладів фіксації). Але жоден одиничний запит
(ні оригінальний, ні переформульований CRAG-кроком) не піднімає більше
1-2 з них одночасно в топ-6 — питання зачіпає п'ять різних аспектів
(ліміт швидкості, вид фіксації, вимоги до приладу, права водія на
місці, порядок оскарження), а `self_rag.py` робить **один** пошук (плюс
один rewrite) на весь запит.

**Той самий запит через `rag_agentic.py`** — агент сам розбив питання на
5 окремих пошуків:

```
пошуки агента: ['швидкість у населеному пункті обмеження',
                'перевищення швидкості штраф відповідальність',
                'докази фіксація порушення камера',
                'протокол про адміністративне правопорушення права водія',
                'автоматична фіксація порушень ПДР постанова без складання протоколу']
```

І дав відповідь по суті: назвав ліміт (п. 12.4 ПДР — 50 км/год, отже
перевищення 23 км/год), статтю й розмір штрафу (ст. 122 КУпАП), пояснив
різницю між автоматичною фіксацією камерою (протокол не складається,
постанова поштою) і особистою зупинкою патрульним (протокол складається
на вимогу), порадив попросити показати дані приладу і згадав строк
оскарження 10 днів (ст. 289 КУпАП) — саме той рівень деталізації, який
очікував користувач.

**Висновок.** Це не баг парсера чи індексації — норми проіндексовані
коректно, `verify.py` для КУпАП (8073-10) чистий. Це структурна межа
`self_rag.py`: один retrieval на весь запит добре працює на прямому
питанні («яка швидкість дозволена»), але губиться на складеному
(«швидкість + доказ + процедура»), бо жоден одиничний ембединг-запит не
близький одночасно до п'яти різних статей. `rag_agentic.py` існує саме
для цього класу питань.

**Зроблено, крок 1.** Бот (`bot.py`) переведений з
`self_rag.answer_with_gate()` на `rag_agentic.run_agentic()` повністю —
свідомо обрано якість відповіді над вартістю. Той самий запит через
agentic (перевірено дослівно): 3 turns (модель батчила по кілька
`search_kb` за раз, не по одному на turn), повна відповідь із лімітом
швидкості, статтею й штрафом (ст. 122 КУпАП), різницею автоматична/
особиста фіксація, правами при протоколі (ст. 256, 268 КУпАП) і строком
оскарження (ст. 289 КУпАП) — рівно той рівень деталізації, який очікував
користувач. `MAX_TOKENS` піднято 800→1200 (структурована відповідь у
кілька розділів ризикувала обрізатися) і `MAX_TURNS` 6→8 (5 пошуків +
фінальна відповідь — це рівно 6, без запасу на складніше питання).

**Зроблено, крок 2 — router.py.** Постійний agentic для будь-якого
питання платить дорожче навіть там, де це не потрібно — просте пряме
питання («яка швидкість дозволена») self_rag закриває за 1-2 виклики
моделі. Додано `router.py`: дешевий класифікатор (`MODEL_FAST`, той
самий каскад, що й grade/rewrite) визначає ПРОСТЕ/СКЛАДЕНЕ, і лише
складене йде одразу в agentic. Перевірено дослівно на обох випадках:

```
Питання: «Яка дозволена швидкість руху у населеному пункті?»
класифікація: ПРОСТЕ
конвеєр: self_rag (класифіковано як просте)

Питання: «Я іхав на своїй машині по місту 73 км на годину і мене
зупинили і кажуть що я перевищів швидкість але не показують докази з
камери яка фіксує швидкість»
класифікація: СКЛАДЕНЕ
конвеєр: agentic (класифіковано як складене)
```

Підстраховка на випадок помилки класифікатора: якщо він визначив питання
як ПРОСТЕ, а `self_rag` усе одно ескалював (`result["escalated"]`) —
`router.answer()` не повертає людині відмову одразу, а пробує agentic як
останню спробу. Найдорожчий шлях (класифікація + невдалий self_rag +
повний agentic) трапляється лише на помилці класифікації, не на кожному
питанні — прийнятна ціна за те, щоб жодне питання, яке агент реально міг
закрити, не пішло в чесну відмову через хибний ПРОСТЕ-вердикт.
`self_rag.py`/`rag_agentic.py` лишаються в проєкті як окремі CLI —
`router.py` лише координує, коли який викликати.

**Зроблено, крок 3 — посилання на джерело в кожній відповіді.** Дані для
цього вже були в кожному витягу з бази знань (`knowledge_qdrant.retrieve()`
дописує `source_url` з точним якорем на абзац — `ingest.py`: `url +
c["anchor"]`), просто `BASE_PROMPT` не просив модель їх показувати. Додано
інструкцію: наприкінці відповіді — розділ «Джерела:» з посиланнями саме на
ті витяги, якими модель реально скористалась (без дублів, без зайвого).
Перевірено дослівно на тому самому складеному питанні — 5 джерел, кожне
підписане статтею:

```
Джерела:
- https://zakon.rada.gov.ua/laws/show/1306-2001-п#n503 (п. 12.4 ПДР — обмеження швидкості в місті)
- https://zakon.rada.gov.ua/laws/show/8073-10#n927 (ст. 122 КУпАП — відповідальність за перевищення швидкості)
- https://zakon.rada.gov.ua/laws/show/8073-10#n4072 (ст. 251 КУпАП — докази)
- https://zakon.rada.gov.ua/laws/show/8073-10#n4219 (ст. 256 КУпАП — зміст протоколу та ваші зауваження)
- https://zakon.rada.gov.ua/laws/show/8073-10#n4329 (ст. 268 КУпАП — права особи, яка притягається до відповідальності)
```

**Зроблено, крок 4 — обрізання відповіді й хибна відмова.** Реальний
кейс користувача: питання «що треба, щоб відкрити бізнес» дало відповідь,
обрізану на півслові. Причина — не Telegram: `run_agent()` у
`core/agent.py` вважав БУДЬ-ЯКИЙ `stop_reason != "tool_use"` завершеною
відповіддю, включно з `"max_tokens"` (модель реально впиралась у ліміт і
зупинялась на півслові) — це мовчки віддавалось як `outcome: "ok"`.
Виправлено: `stop_reason == "max_tokens"` тепер позначається окремо
(`outcome: "truncated"`), `bot.py` дописує користувачу чесне пояснення
замість тиші. `MAX_TOKENS` піднято 1200→1800, а `BASE_PROMPT` тепер прямо
просить компактність для чату (3-4 пункти замість вичерпного переліку,
без ВЕЛИКИХ ЗАГОЛОВКІВ і роздільників «---») — сама причина, чому
1200 не вистачало на розлогу структуровану відповідь.

Ця ж правка ледь не спричинила **новий, гірший баг**: одразу після зміни
той самий запит про бізнес почав узагалі не шукати (`kb_searches: []`) і
відмовляв, вважаючи тему поза спеціалізацією — хоча потрібні закони
(755-15, Податковий кодекс, закони про ліцензування) реально
проіндексовані. Причина — стара фраза в `BASE_PROMPT` «(зокрема ПДР,
ККУ, КУпАП, КПК, Конституція)» (залишок з часів, коли в базі й справді
було лише кілька документів) у комбінації з новою інструкцією про
компактність модель прочитала як вичерпний список спеціалізації й
відмовилась навіть пробувати. Виправлено: прибрано застарілий закритий
перелік, додано пряму заборону відмовляти без хоча б одного виклику
`search_kb` (`rag_agentic.py`). Перевірено дослівно — тепер шукає (4
пошуки), знаходить правильні закони і дає компактну (2243 символи проти
розлогої версії з обрізанням) структуровану відповідь із джерелами.

**Висновок для майбутніх правок промпту:** кожна зміна `BASE_PROMPT`
перевіряється не лише на питанні, яке спричинило правку, а й на 1-2
раніше працюючих кейсах — стислість і повнота тягнуть у різні боки, і
щось із раніше перевіреного може мовчки зламатися.

## Нюанси для обговорення

- **fail-closed за замовчуванням.** І `domain/knowledge.py`, і
  `knowledge_qdrant.py` повертають порожньо, якщо нічого не пройшло
  поріг — на відміну від `module2`, де лексичний baseline навмисно
  fail-open. Для юридичної теми ціна вигаданої відповіді вища, ніж ціна
  чесного «не знаю».
- **Оновлення при зміні закону.** `watch.py` знаходить нову редакцію
  автоматично, але переіндексація — ручний крок, і завжди всі документи
  разом: ID точок — наскрізний лічильник по всіх чанках, не прив'язаний
  до конкретного джерела. Виправдано зараз (6 документів, кілька хвилин);
  варте переробки на точкове оновлення одного джерела, якщо їх стане
  багато (SQLite `documents`/`clauses` уже розділені по document_id —
  найважча частина точкового оновлення вже готова).
- **PostgreSQL замінить SQLite тим самим шляхом, якщо колись знадобиться**
  (`db.py` — звичайний SQL, не залежить від діалекту): апгрейд пізніше —
  заміна connection string, схема не зміниться.
- **Двоетапний retrieval (спершу документ, потім стаття)** — з 6
  документами вже має сенс, поки не реалізовано: `document_id` є в
  payload Qdrant як готовий фільтр, лишається додати крок класифікації
  запиту на «який(і) акт(и) сюди стосуються» перед пошуком статті.
- **RAG ≠ дії.** Агент лише консультує — інструментів на кшталт «подати
  скаргу» немає. `rag_agentic.py` показує механізм tool-use на прикладі
  пошуку; той самий `run_agent()` підійде і для дійових інструментів.
- **Масштаб навмисно обмежений.** Список актів українського права
  величезний (сотні кодексів/законів, тисячі підзаконних актів). Ця
  партія — 6 документів, тематично близьких одне до одного і до
  початкової мети бота; розширення — партіями, з перевіркою кожного
  нового профілю структури на реальному тексті перед масовим
  застосуванням (саме так знайдені всі три баги вище).
